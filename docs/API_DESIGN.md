# REST API Design Specification

This document defines the proposed future HTTP API endpoints for the Hospital Resource Intelligence platform. These specifications will guide the implementation in Stage 10B.

> [!IMPORTANT]
> **Implementation Scope:**
> This document details design mockups and endpoint logic. **No FastAPI routes or active servers must be created during Stage 10A.**

---

## 1. REST API Endpoints

### A. GET `/api/forecast/icu`
* **Purpose:** Retrieves the 7-day predicted ICU bed occupancy alongside actual occupancy (where available) and model prediction ranges.
* **Method:** `GET`
* **Parameters:**
  - `model` (optional string): Filter predictions by model (`'XGBoost'`, `'Prophet'`, or `'LSTM'`). Defaults to the best operational model (`'XGBoost'`).
* **Database Table Used:** `forecasts` table.
* **Expected Response (`200 OK`):**
  ```json
  {
    "resource": "ICU Beds",
    "model": "XGBoost",
    "forecast_horizon": "7 days",
    "predictions": [
      {
        "date": "2137-10-11",
        "predicted_demand": 0.2041,
        "actual_demand": 0.0,
        "created_timestamp": "2026-08-28T00:00:00Z"
      },
      {
        "date": "2137-10-12",
        "predicted_demand": 0.2370,
        "actual_demand": 1.0,
        "created_timestamp": "2026-08-28T00:00:00Z"
      }
    ]
  }
  ```

### C. GET `/api/alerts`
* **Purpose:** Retrieves all resource shortage alerts generated by comparing predictions with capacity limits.
* **Method:** `GET`
* **Parameters:**
  - `risk_level` (optional string): Filter by `'LOW'`, `'MEDIUM'`, or `'HIGH'`.
* **Database Table Used:** `alerts` table.
* **Expected Response (`200 OK`):**
  ```json
  {
    "alerts": [
      {
        "alert_date": "2137-10-11",
        "resource": "ICU Beds",
        "predicted_demand": 0.2041,
        "actual_capacity": null,
        "simulated_capacity": 2.0,
        "is_capacity_simulated": true,
        "capacity_gap": 1.7959,
        "risk_level": "LOW",
        "reason": "Predicted demand is within safe capacity bounds."
      }
    ]
  }
  ```

---

### D. GET `/api/recommendations`
* **Purpose:** Retrieves operational recommendations mapped to the resource alerts.
* **Method:** `GET`
* **Database Table Used:** `recommendations` joined with `alerts`.
* **Expected Response (`200 OK`):**
  ```json
  {
    "recommendations": [
      {
        "date": "2137-10-11",
        "resource": "ICU Beds",
        "risk_level": "LOW",
        "recommendation": "Current predicted demand is within available capacity. Continue routine monitoring.",
        "trigger": "Predicted demand matches safe operational thresholds.",
        "model": "XGBoost",
        "alert_id": 1
      }
    ]
  }
  ```

### E. GET `/api/explanations/icu`
* **Purpose:** Retrieves SHAP or LIME local feature contributions for the specified forecast dates to explain ICU model predictions.
* **Method:** `GET`
* **Parameters:**
  - `date` (required string): YYYY-MM-DD target prediction date.
  - `method` (optional string): `'SHAP'` or `'LIME'`. Defaults to `'SHAP'`.
* **Database Table Used:** `explanations` table.
* **Expected Response (`200 OK`):**
  ```json
  {
    "resource": "ICU Beds",
    "date": "2137-10-11",
    "model": "XGBoost",
    "explanation_method": "SHAP",
    "explanations": [
      {
        "feature": "occupied_beds_lag_1",
        "feature_value": 1.0,
        "contribution": 0.3098,
        "direction": 1
      },
      {
        "feature": "month",
        "feature_value": 10.0,
        "contribution": -0.1607,
  ```

## 2. Security & Architectural Guidelines

### A. Environment Configuration
* **No hardcoded credentials:** Credentials must be loaded from system environment variables via `.env` (using Python's `os.environ` or `pydantic-settings`).
* **Example env file structure:**
  ```env
  DATABASE_URL=postgresql://db_user:secure_password@localhost:5432/hospital_intelligence
  API_PORT=8000
  CORS_ORIGINS=["http://localhost:3000"]
  ```

### B. Prevention of SQL Injection
* **Parameterized Queries:** Use database driver placeholders (e.g. `%s` in `psycopg2` or bind parameters in `SQLAlchemy`) to insert variables.
* **ORM usage:** Limit raw SQL string concatenations; favor high-level ORM operations where appropriate.

### C. Input Validation
* **Pydantic Schemas:** Declare strict API requests and response schemas using Pydantic models to assert correct date string formats (`YYYY-MM-DD`), resource names, and model parameter boundaries. Invalid requests must immediately trigger a `400 Bad Request` or `422 Unprocessable Entity` status before database lookup.

### D. CORS (Cross-Origin Resource Sharing)
* **Explicit Whitelisting:** Enforce explicit CORS whitelists mapping to verified client domains (e.g., React frontend local development urls). Avoid using `allow_origins=["*"]` in production.

### E. Authentication & Clinical Safety
* **JWT Authentication:** Secure administrative endpoints with JSON Web Tokens (JWT) using `OAuth2` password flow.
* **Disclaimer Header:** The API will automatically append a custom header `X-Clinical-Notice: Operational metrics only. Systems must not be used for diagnosis or patient treatment decisions` on all response payloads to reinforce clinical boundaries.
